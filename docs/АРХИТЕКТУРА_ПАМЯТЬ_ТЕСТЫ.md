# Архитектура проекта, карта памяти ESP32-C6, тесты

## 1. sdkconfig и sdkconfig.ci
- `sdkconfig` - основной файл конфигурации проекта, генерируется/редактируется через `idf.py menuconfig`. Содержит все Kconfig опции. Должен быть в корне проекта. Коммитить в git (чтобы воспроизводить сборку).
- `sdkconfig.ci` - файл конфигурации для CI (автотестов). Может быть пустым или содержать переопределения для конкретного CI job. У нас пустой - ок. Если не используется в CI, можно оставить пустым либо удалить. В ESP-IDF примерах он часто присутствует.

Место верное - корень проекта.

## 2. Правильная архитектура директорий ESP-IDF
Базовый вариант:
```
<project>/
├── CMakeLists.txt        # корневой
├── sdkconfig             # конфиг
├── main/                 # основное приложение
│   ├── CMakeLists.txt
│   ├── main.c (или app_main.c)
│   └── Kconfig.projbuild # опц. свои menuconfig опции
├── components/           # свои переиспользуемые компоненты
│   └── my_component/
│       ├── CMakeLists.txt
│       ├── include/
│       └── src/ (или *.c в корне компонента)
├── managed_components/   # от Component Manager (в .gitignore)
├── build/                # артефакты (в .gitignore)
├── partitions.csv        # опц. кастомная таблица разделов
└── pytest_*.py или tests/ # тесты
```

Рекомендации:
- Весь исполняемый код приложения - в `main/` или в своих компонентах в `components/`
- Общие драйверы/библиотеки выносить в `components/` для переиспользования
- Конфиги, тесты не класть в `build/`
- `managed_components/` управляется Component Manager

## 3. Карта памяти ESP32-C6 (кратко)
ESP32-C6 имеет встроенную флеш 4MB (у нашей платы). Типичная раскладка для default partition table (factory app):
| Раздел | Адрес | Размер | Назначение |
|---|---|---|---|
| bootloader | 0x0000 | ~24-32KB | Вторичный загрузчик ESP-IDF |
| partition-table | 0x8000 | 4KB | Таблица разделов |
| nvs | 0x9000 | 24KB | Non-Volatile Storage (настройки) |
| phy_init | 0xf000 | 4KB | RF калибровка |
| factory/app | 0x10000 | ~1MB+ | Основное приложение |
| (ota_0/ota_1) | зависит | зависит | Если используется OTA |
| spiffs/littlefs | зависит | зависит | Файловая система (опц.) |

У нашей текущей прошивки:
- bootloader @ 0x0
- partition table @ 0x8000
- factory @ 0x10000 (1MB)

Посмотреть текущую таблицу: `get_idf && cd ~/Projects/esp32/C6_SuperMini && python ~/.esp/esp-idf/components/partition_table/gen_esp32part.py build/partition_table/partition-table.bin`

### Как прошивать
Стандартный порядок (если прошиваем вручную): bootloader, partition-table, app
```bash
idf.py -p /dev/ttyACM0 write-flash \
  0x0 build/bootloader/bootloader.bin \
  0x8000 build/partition_table/partition-table.bin \
  0x10000 build/PROJECT_NAME.bin
```
Или просто `idf.py -p /dev/ttyACM0 flash` - сам определит адреса из `flash_args`.

### Как оценить занятое место
```bash
get_idf && cd ~/Projects/esp32/C6_SuperMini && idf.py size
idf.py size-components
idf.py size-files
```

### Несколько проектов на одной плате
На одной плате может быть только **одно активное приложение** в выбранном разделе. Варианты:
1. **Один проект** - прошивать в `factory` (простейший)
2. **OTA** - использовать `ota_0`/`ota_1`, переключение через bootloader
3. **Полная перезапись** - просто прошить новый `factory` целиком (старая прошивка будет перезаписана)

Если прошивать поверх - занимает то же самое место по адресу. Если нужно "держать" несколько прошивок одновременно - только через OTA с партициями или хранить бэкапы и перешивать.

### Новая плата
Абсолютно чистая ESP32-C6 **не имеет** валидного ESP-IDF bootloader'а в пользовательском смысле. ROM bootloader есть всегда (встроен в чип). Он умеет входить в download mode (UART/USB) и принимать прошивку через esptool. Чтобы загрузиться с флеша в нормальном режиме нужен корректный **2nd stage bootloader** + **partition table** + **app**.

То есть "чистая" плата = только ROM bootloader. Для старта под ESP-IDF нужно прошить bootloader+partition table+приложение.

## 4. Тесты (pytest) в ESP-IDF
Файл `tests/pytest_hello_world.py` - пример интеграционного теста на реальном железе/QEMU. Он использует `pytest-embedded-idf`.

### Как запускать
```bash
get_idf
pip show pytest pytest-embedded pytest-embedded-idf 2>&1 | head -10
```
Если не установлены - ставить через requirements ESP-IDF или в venv.

Пример запуска на подключённой плате:
```bash
cd ~/Projects/esp32/C6_SuperMini
pytest tests/pytest_hello_world.py --target esp32c6 -p esp-idf 2>&1 | tail -40
```
Или с указанием порта - зависит от настроек `pytest-embedded`.

### Рекомендации по структуре тестов
- Тесты класть в `tests/` или `pytest/` в корне проекта
- Unit-тесты можно использовать через `unity` компонент ESP-IDF
- Для большинства прикладных проектов новичку достаточно ручного тестирования через `idf.py monitor`

Больше инфо:
- [pytest-embedded](https://docs.espressif.com/projects/pytest-embedded/)
- [Unit Testing](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32c6/api-guides/unit-tests.html)

## 5. Практика: добавляем тест под пример
1. Пишем код в `main/` или в компоненте
2. Собираем: `idf.py build`
3. Добавляем тест в `tests/test_*.py` с использованием `pytest_embedded_idf.dut`
4. Запускаем из активированного `.venv` + `get_idf`

Пример минимального теста (проверка лога):
```python
import pytest
from pytest_embedded_idf.dut import IdfDut

@pytest.mark.generic
def test_my_example(dut: IdfDut):
    dut.expect("Старт ESP32-C6", timeout=10)
```
